# Домашнее задание к занятию «Базы данных, их типы»
### Задание 1. СУБД

1.1. Целостность и чёткая структура — это про реляционные СУБД (PostgreSQL, Oracle, MS SQL). Там строгая схема, ACID-транзакции, внешние ключи — как раз то, что нужно для бюджетов и финансовых отчётов.

1.1*. Если хеширование занимает много времени — можно сменить хеш-функцию на более быструю, например xxHash. Либо вынести хеширование в отдельное API с аппаратным ускорением.

1.2. Для лендингов и CRM лучше NoSQL — она гибкая и быстрая. Лиды с произвольной структурой удобно писать в документную MongoDB, а для CRM можно взять ту же NoSQL, если схема часто меняется.

1.2*. Да, можно закрыть одной СУБД — PostgreSQL с JSONB. Лиды храним в JSONB (гибко), CRM — в обычных таблицах. Получаем и гибкость NoSQL, и целостность реляционной модели.

1.3. Для базы норм и обучающих материалов достаточно реляционной СУБД с простой схемой. Иерархическая подошла бы лучше по структуре, но при изменении структуры компании её пришлось бы сильно переделывать, поэтому реляционная практичнее.

1.3*. Да, СУБД из задания 1.1 вполне справится — достаточно создать отдельную БД (или схему) именно под эту задачу.

1.4. Хотя очевиднее графовая СУБД, я бы выбрал документо-ориентированную: на каждую задачу создаётся документ со всеми аргументами, и при этом можно добавлять связи между задачами. Если графы сложные — тогда Neo4j.

1.4*. Да, отдел закупок спокойно можно подключить к этой СУБД — просто отдельными коллекциями/таблицами.

1.5*. В теории можно решить всё одной реляционной СУБД, но структура получится невероятно сложной, а работать будет неэффективно. Так что скорее нет, чем да.

### Задание 3. SQL vs NoSQL

3.1. Единый язык для множества реализаций; чёткая и определённая структура; целостность данных; транзакции; нормализация.

3.1*. NewSQL берёт лучшее с обеих сторон: масштабируемость и распределённость как у NoSQL, но при этом сохраняет SQL-интерфейс и ACID-транзакции как у SQL (CockroachDB, TiDB, Spanner).

###Задание 4. Кластеры

Основными критериями для выбора будут хорошая поддержка кластеризации и хорошая работа с кешем — чтобы быстрее производить однотипные вычисления. Я бы выбрал модель PA (устойчивость к разделению и доступность) и принцип BASE, так как при большом объёме данных системе важно «не захлебнуться». Для самих вычислений — MapReduce-подобная модель (Spark) поверх распределённого хранилища.
